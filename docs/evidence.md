# Add and review proof

Members with a verified email can sign in at `/check/sign-in`, then use `/add` and `/review`. Account creation remains closed in production. These screens use the same actions as the other callers; each action checks the account inside the server.

A member can type work, pay, volunteer, work program or school facts. Blanks stay unknown. Saving makes a proposed line. A separate confirmation records the reviewed facts. Editing a confirmed line returns it to proposed. Rejected lines stay in the history and can be restored through editing. Every change checks the version and writes its history in the same database transaction.

A duplicate warning compares the proposed line with current confirmed lines. “These are separate” records the IDs and versions the member reviewed. Changed comparisons must be reviewed again. The HTTP action uses the framework's structured error type so the browser receives that comparison.

## Files

Uploads accept JPEG, PNG, WebP, HEIC and PDF, up to 15 MB each. Photos are limited to 40 million pixels; PDFs to 40 pages. Password-protected and unreadable files are refused. Content is checked by the decoder, rather than trusting the file name or browser type. The request body is also bounded on the server and in Caddy.

The phone makes a smaller JPEG viewing copy, with a longest side of 2,400 pixels, when its browser can decode the image. The server handles HEIC when the phone cannot. For normal-sized files, the full original crosses the connection and is kept unchanged. Oversized JPEG, PNG and WebP files follow the smaller-copy path described below. EXIF rotation is applied to the viewing copy. The member can turn a sideways photo before saving. The original's bytes remain unchanged.

Darkness and blur checks produce warnings, never evidence or a decision. The member can retake the photo or explicitly say its facts are readable. A check and a retake write no file or database row. The server repeats the check before saving. PDF pages are rendered one at a time with local PDF.js code, without running document scripts or rendering links and forms. Page controls, rotation and size controls work on a phone. The original can be downloaded through the signed-in account.

Only original bytes are stored, through the framework's encrypted private storage. The app selects its app-owned `hosted-private` bucket and registers the provider at startup; member requests do not borrow a deployment owner's generic storage credentials. The database requires an encrypted, opaque handle. Viewing copies are made in memory and are not saved. Reads check both the verified browser session and the member's ownership. Responses use `private, no-store`. No storage handle or public document URL is returned to the browser. SHA-256 detects a repeated file within that member's account. Limits are 200 files and 300 MB per member.

An unused file, or a file linked only to rejected evidence, can be deleted. Proposed or confirmed lines keep their files as proof. Storage failures leave manual entry available.

## Reading documents

After a member saves a photo or PDF, the evidence screen reads it on its own and shows "Reading your document…" while it waits. The member's own agent can ask for the same reading. The reader proposes facts: dates, hours, employer and pay amounts. It never decides a month. Every reading is saved as proposed lines through the same path as typed entry, with versions and duplicate warnings. Nothing counts until the member confirms a line in the browser; the reader and the agent cannot confirm, and the reader cannot confirm business costs.

The app uses the model the deployment already has, through the framework's one-off completion call. Photos are sent as the same decoded, size-limited copy the upload check makes, with rotation applied. A PDF is drawn page by page on the server; only the first 10 pages are read, and the screen says so. The document goes to the model as fenced data with plain instructions that its text is never an instruction.

The answer must be one exact JSON object. Anything else, extra fields, a confirmed status or owner, impossible dates, dates outside the document's own period, negative or fractional-cent amounts, hours that fail the hours check, or more than 60 lines make the whole read fail: the member sees "We couldn't read this. You can type the numbers instead." with typed entry open. A fact the model is unsure of is left blank and listed as a question. A line with questions or below 0.85 confidence is marked "Check this". A document that is not a US record gives "We can't read this as a US pay stub." A file is read into lines once; reading it again adds nothing.

Each call adds one row to `eighty_ai_ledger` with the purpose and token counts only, never document content or numbers. Saved files are kept as described above, until the member removes them.

Before a photo leaves the phone, the member can black out parts of it, such as a name, case number or account numbers, by dragging boxes or by keyboard. The boxes are painted into a new copy on the phone; only that copy is sent, without camera metadata.

Try mode reads one document for a visitor with no account. It is checked with the same size limits, read in memory, never written to the database or storage, and cleared as soon as the answer is ready. The page says when it was deleted. The numbers fill the try form for the visitor to check and confirm. The ledger keeps only that a try happened. Each visitor can read 3 documents a day and the site 50 a day, set with `EIGHTY_TRY_READS_PER_VISITOR` and `EIGHTY_PUBLIC_MODEL_USES_PER_DAY` (the older daily setting also works); 0 turns reading off. Per-visitor counts are kept in memory under a keyed hash of the address and reset on restart. When a limit is reached, try mode still works by typing and says so.

Tests replace only the model engine. Parsing, refusals, fencing, page limits, saving, owner checks, the ledger and try mode run as real code against a disposable database. These tests do not measure reading accuracy.

## Checks

`pnpm test` includes generated image rotation, resizing, metadata removal, dark and blurred photos, HEIC conversion, PDF page limits and malformed uploads. Fixtures contain made-up pay facts only. The HEIC fixture was encoded from `tests/fixtures/documents/pay.png` using the supplied Dockerfile and `heif-enc`.

`pnpm check:production IMAGE` creates a separate database and two verified browser accounts. It checks English and Spanish at 360 px, file inspection and retake, encrypted storage, exact original bytes, ownership, multiple PDF pages, manual evidence, confirmation, duplicate comparisons, editing, rejection and restoration. Its private-storage transport runs only in that disposable container; encryption and decryption use the real provider. `pnpm check:storage` separately checks the configured private bucket.

Remaining launch limits: there is no independent database backup, and the file encryption key exists only on this server. Set `EIGHTY_REGISTRATION_ENABLED=1` with email configured to offer accounts. See [the practice reading results](tests/results/reading.md).

## File size and removal safeguards

Both upload actions set `maxBodyBytes` to the base64 size of a 15 MB file plus 1 KB for JSON. The framework rejects an excessive Content-Length before reading the body and stops a chunked body when it crosses the limit. Caddy also limits `/_agent-native/actions/*` to 22 MB. `pnpm check:production` proves the 413 with the headers of a real signed-in page request, sending a Content-Length one byte over the limit and no body; the same request without those headers must get 403, and a small valid request must reach the action.

A JPEG, PNG or WebP over 15 MB or 40 million pixels is made smaller on the phone before upload. The saved JPEG has a longest side of at most 4,000 pixels, with orientation applied and quality 0.9. If needed, the phone reduces the dimensions again to stay under 15 MB. The page says before saving that it will keep a smaller copy, and confirms that after saving. The full original stays on the member's phone. Normal-sized uploads remain byte-for-byte unchanged. Oversized PDF and HEIC files give steps for splitting the PDF, choosing a lower photo size or saving a JPEG; manual entry remains available.

A file can be removed when it has no evidence lines or every linked line is rejected. A proposed or confirmed line still protects it. The database transaction removes the document row and writes a member event and an encrypted storage-deletion record together. Only after commit does the app delete the stored file. Storage failure leaves the deletion record for retry, and the member sees that deletion is pending. The framework's interval job checks due records every minute, with retries backing off to at most one hour. The record is removed only when storage confirms deletion; a failed acknowledgment is safe to retry too.

## Decoding memory

A large photo can need about 160 MB of memory to decode, so the server reads at most two documents at a time. Other uploads and file views wait up to 30 seconds for a free slot, then get a clear message to try again in a minute.

## Member months

After sign-in, `/months` shows this month and last month, then older months with confirmed proof, newest first. Each month shows the status, hours toward 80 or income toward $580, and a link to the federal rule. The state makes the decision. `/months/YYYY-MM` shows the reason, counted lines, dates, hours, pay and source, plus questions about missing facts. The add and review links show how many lines need review. Both screens use English or Spanish.

`check_month` reads only the signed-in member's profile and evidence, using the same ownership restrictions as `list_evidence`. It also requires the verified browser review identity used by `confirm_evidence`; the agent cannot call it. Proposed and rejected lines never enter the member calculation. The example and member calculations share `server/lib/month-input.ts` and the existing month rules.

Members can answer missing coverage questions on the month page. Answers use the signed-in account action and saved member profile. A member with 80 confirmed work hours sees “Meets” when the coverage facts place them within the rule. An unknown coverage answer stays “Not sure yet”. The rules remain unchanged. Bad or future months use the rule's own reason. No coverage decision is promised.

Signed-out GET and HEAD member pages redirect to sign-in with a same-site return path and the language. `/example` opens the home page's example title. Data requests and actions still require sign-in. A example visitor opening a month page returns to `/example`.
